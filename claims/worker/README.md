# Claims Temporal worker

English | [中文](README.zh.md)

The Cordis `claims-worker` profile owns this module's lifecycle. Do not start a separate product entrypoint; use `claims/runtime/launch.mjs` with `DSH_PROFILE=claims-worker`. Installation is `npm --prefix claims/worker ci --workspaces=false --ignore-scripts`; this private demo dependency tree is separate from the managed pnpm packages.

`startWorker({address, namespace, taskQueue, workApiUrl, serviceToken, dispatchPollMs, onError})` returns `{done, stop}`. Defaults are `temporal:7233`, namespace `default`, queue `claims-work`, and a 2000 ms poll interval. `workApiUrl` and a resolved private `serviceToken` are required. The profile resolves `WORKER_API_TOKEN_FILE` or `WORKER_API_TOKEN` before invoking it. `onError` defaults to a bounded stderr diagnostic and observes transient poll failures; permanent API/authentication/JSON failures reject `done`. The worker preflights both outboxes before starting, retries transient polling failures until stopped, and never drops or ACKs a failed delivery. The profile must observe `done` and await the idempotent `stop()` on disposal; stop drains the worker and poller before closing their connections.

`submitClient({address, namespace, taskQueue})` connects a trusted gateway to the same namespace and queue. `submit({operationId})` starts reviewed execution, and `startWage({requestId,workItemId})` starts a previously admitted wage request. Both return `{workflowId,runId,alreadyStarted,closed}` and reject workflow-ID reuse while Temporal retains the execution history. The domain's durable operation/receipt ledger remains the duplicate-effect protection after history retention expires. `signalWageEvidence({requestId,eventId})`, `signalWageReview(requestId)`, `requestReconciliation(operationId)`, and `reconcileWage(requestId)` deliver signals; they do not grant claim access or approve work. `status(workflowId)` queries progress, `result(workflowId)` awaits completion, and `close()` releases the connection. Identifiers are restricted opaque strings; custom `partnerTimeoutMs`, `reviewTimeoutMs`, and `reconciliationTimeoutMs` are positive milliseconds bounded to 30 days. Omitted values use the workflow defaults documented in deployment instructions. Workflow input changes on a duplicate start do not replace the original input.

All activities call authenticated internal API routes with bounded HTTP/activity retries. The work API owns idempotency, authority, and effect receipts. A process failure can occur after a destination effect but before an activity result; persistence of the operation ID and explicit `unknown` reconciliation are required even though Temporal replays deterministic workflow history. See [deployment and recovery](../deploy/README.md) for the route sequence, fixtures, timers, and executable checks.
